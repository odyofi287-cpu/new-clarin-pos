Deployment guide — Free hosting via Oracle Cloud Always Free VM

This repo contains a Node.js Express backend (`server/`) and a Vite React frontend (`client/`). The Dockerfile builds the client and places the static `dist` into `server/dist`, then starts the server.

Recommended path for this SQLite-backed app (Oracle Cloud):

1. Create an Ubuntu VM.Standard.E2.1.Micro or Always Free Ampere A1 VM in Oracle Cloud.
2. Install Docker on the VM and clone this repository.
3. Build and run the production container with a persistent database volume:

    ```bash
    docker build -t new-clarin-pos .
    docker volume create new-clarin-pos-data
    docker run -d --name new-clarin-pos \
       --restart unless-stopped \
       -p 4000:4000 \
       -e NODE_ENV=production \
       -e PORT=4000 \
       -e JWT_SECRET='replace-with-a-long-random-secret' \
       -e CORS_ORIGIN='' \
       -e SEED_INITIAL_DATA=true \
       -v new-clarin-pos-data:/app/server/data \
       new-clarin-pos
    ```

4. Open TCP port 4000 in the Oracle VCN security list, or put Nginx in front of the container and expose only ports 80/443.
5. After the first login and production-user setup, recreate the container with `SEED_INITIAL_DATA=false`.
6. Verify `https://your-domain.example/api/health` and the login page.

The Docker volume is required. Without it, the SQLite database disappears when the container is replaced.

Alternative quick path (Render.com container service):

1. Push this repository to GitHub.
2. Sign up at https://render.com (free tier available) and connect your GitHub account.
3. Create a new "Web Service" and choose "Docker" as the environment.
   - Select your repository and the branch to deploy.
   - Render will detect the `Dockerfile` and build the container.
4. Environment variables (set in Render dashboard):
   - `NODE_ENV=production`
   - `JWT_SECRET` — set a secure secret for JWT signing (required for auth).
   - `CORS_ORIGIN` — optional allowed frontend origin; same-origin access is used by default.
   - Optionally `PORT` (Render provides one; the app falls back to 4000).
5. For persistent data (SQLite file) either:
   - Use Render persistent disks (attach a disk and configure `server/data` to be mounted), OR
   - Use a managed DB (Postgres) and adapt `server/db.js` to use Postgres instead of SQLite. For a short-lived demo, the container-local SQLite database is acceptable but will be lost on redeploys.

Alternate hosts:
- Railway.app — supports Docker and Node deployments; connect GitHub and select Docker.
- Fly.io — supports Docker and volumes (for SQLite persistence).
- Netlify / Vercel — frontend-only (use these if you want only the client deployed); server can be left for Render/Railway.

GitHub Actions (optional):
- You can use the included `.github/workflows/ci-build.yml` to build and publish a container image to GitHub Container Registry (GHCR). If you publish to GHCR, you can configure Render to deploy from the image instead of building from the repo.

Notes and caveats:
- The app uses `better-sqlite3` in production. Building that package inside the Docker image will work (it's compiled during `npm ci`), but ensure the build environment supports the native build tools. The Docker base image used here is `node:20-bullseye`, which is more reliable for native modules than Alpine.
- For public demos consider switching to a managed database for persistence and scalability.

Use Render with the included `render.yaml`.

### 2) Create service from Blueprint

- Connect your GitHub repo and select the branch
- Render will detect `render.yaml` and create one web service:

   - Plan: `free`
   - Env: `docker`

### 3) Environment variables

### 4) Deploy and smoke test

   - You can sign in and open Dashboard / POS views

### 5) Persistence check
- Create a sample pickup record.
- Trigger a redeploy.

## Notes for truly free operation

- Free services may sleep during inactivity and take time to wake.
- This app currently uses SQLite (`server/data/pos.db`), so the attached disk is required for persistence across redeploys.
- The included seed users are convenient for demo usage; if this will be public, rotate credentials and restrict access.

## Production Safety Hardening (Recommended)

1. Keep seeding enabled only for first boot:
   - `SEED_INITIAL_DATA=true`
2. Log in and create your real production users.
3. Rotate/remove default seeded accounts and passwords.
4. Disable future startup seeding:
   - Set `SEED_INITIAL_DATA=false` in Render environment variables.
5. Redeploy and verify:
   - Existing users remain unchanged.
   - No default credentials are re-applied on restart.

Important:
- With `SEED_INITIAL_DATA=false`, a brand-new empty database will not auto-create users.
- Use this setting after initial bootstrap, not on a fresh empty deployment.
